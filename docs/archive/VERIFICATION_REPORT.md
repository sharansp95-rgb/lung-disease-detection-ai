# VERIFICATION_REPORT.md
Pre-submission fact-check of `SDP_Review1_Report.docx` and `Lung_Disease_Detection_Review1.pptx` against the actual code, data, checkpoints, and logs in this repository, as of 2026-08-28.

---

## Headline finding (Step 0)

**The Report is closer to the truth, but neither document matches the codebase's own internal ground truth (`PROJECT_STATUS.md`, generated 2026-08-25/26 by directly interrogating the running app).** Hard evidence — checkpoint files, `eval_outputs/*_test_metrics.json`, a passing 24-test `pytest` suite, working `/predict/xray` and `/predict/ct` routes, a populated `app.db` — confirms the project **is** trained, integrated, tested, and demoable, so the PPT's "to be measured once trained" / "aims to show" / "next milestones" framing (Slides 5, 7, 17) is **badly outdated**, not honest hedging about the present. But the Report, while directionally right that the project is done, gets a striking number of its own supporting *specifics* wrong: it describes the CT dataset's **pre-leakage-fix** counts and splits (1,097 images) instead of the actual, currently-loaded model's dataset (1,036 images, after a patient-leakage cluster resplit and a protocol-mismatch exclusion — arguably the single most impressive piece of engineering in the project, and one the Report never mentions); its claimed CT accuracy (98.19%) traces to a superseded 5-fold cross-validation run on that same old, leakage-contaminated dataset, not the actual deployed checkpoint (which reproduces to 99.04% val / 98.06% test on the corrected data); its dataset-split methodology description (stratified 70/15/15 via `sklearn.train_test_split`) doesn't match the code (80/10/10 via `random.Random(SEED).shuffle`); and two of its three self-disclosed "weaknesses" (raw exception leakage, no test suite) are already false in the current code.

Document metadata is also worth flagging: the PPT's docx/pptx core properties show it was authored **2026-08-06**, before any training occurred (consistent with its content). The Report's core properties show **created = modified = 2026-08-19** — several days *before* the earliest timestamp on any checkpoint or eval artifact backing its "Done" claims (`checkpoints/xray_best_model_phase35_v2.pt` is dated 2026-08-24 12:13; the CT/segmentation work continued through 2026-08-26). This doesn't prove the Report was literally written before the results existed (docx "created" metadata can be inherited from a template/copy rather than reflecting the true last edit), but it's an anomaly worth being aware of before submission — if the Report file itself wasn't re-saved after 2026-08-19, its numbers predate the actual final training runs.

**Verdict: partial on both — the Report is right about *whether* the project is done, wrong about several specific numbers describing *how*; the PPT is right about its numbers where it commits to any, but wrong (stale) about whether the project is done at all.**

## Real, noteworthy things in the code that neither document mentions

These are gaps in *reporting*, not gaps in the underlying engineering — several are more impressive than anything currently written up:

1. **CT patient-leakage catch and fix.** The original per-image CT split had 35 of 109 test images sharing a near-duplicate slice with a training image (via perceptual-hash + SSIM clustering), which alone explained an initial spurious **100%** test accuracy (`eval_outputs/ct_scan/ct_test_metrics.json`: `test_accuracy: 1.0`). This was diagnosed and fixed with a cluster-aware resplit (`scripts/ct_resplit_grouped.py`, `PROJECT_STATUS.md` §6). Neither document mentions this at all — it's arguably the single strongest piece of evidence of engineering rigor in the whole project, and it's completely absent from both the Report and the PPT.
2. **CT scanner-table shortcut-learning fix.** After the leakage fix, Grad-CAM still showed the model keying off the scanner table/couch structure in 89.3% of Malignant images vs. ~100% for Normal/Benign — traced to a genuinely different acquisition protocol for ~60 images, and excluded (`scripts/ct_table_shortcut_audit.py`, `audit/ct_table_check/`). Not mentioned in either document (the Report's own, different, unverifiable Grad-CAM claim in E1 may be a garbled memory of this).
3. **TB burned-in artifact severity: 53.1% of Tuberculosis images vs. 0.37% of Normal** carried a color-tint/redaction-box artifact correlated with the label — a much starker shortcut-learning risk than either document's framing suggests, and the actual remediation numbers (72 TB images excluded, 146 inpainted, 298 desaturated) are more dramatic than the Report's understated "15 excluded."
4. **Groq model substitution** (Llama 3.3 70B → `openai/gpt-oss-120b`, because the originally-planned model was removed from Groq's catalog) is a real, live technical decision, documented in code comments, that both documents get wrong (D5).
5. **A disclosed, deliberate accuracy trade-off**: switching X-ray preprocessing from border-crop to the trained segmentation model's lung-boundary crop raised overall accuracy 88.3%→95.0% but *dropped* Tuberculosis-class accuracy 93%→87%, because the TB source dataset has no segmentation masks. This nuanced, honestly-reported trade-off (in `PROJECT_STATUS.md` §3) doesn't appear in either document.
6. **Startup-time reproduction checks**: every model checkpoint's claimed accuracy is independently re-verified against live validation data before the FastAPI app is allowed to start (`backend/models.py`), blocking startup on a mismatch. A concrete piece of rigor with no mention in either deliverable.
7. **Per-IP rate limiting** via `slowapi` on prediction/auth routes (`backend/rate_limit.py`) — not mentioned in either document, despite being a real non-functional requirement (D "Scalability"/"Reliability") the Report gestures at abstractly.

## Scores

### Report: **5.5 / 10**

- **Factual accuracy (40%) — weak.** Gets the broad architecture/stack/workflow right, and raw dataset source counts are exact, but a long list of *specific, checkable* numbers are wrong or stale: CT dataset counts/splits describe the pre-leakage-fix data (A3, A5), TB cleanup undercounts exclusions by ~5x (A2), the split methodology (ratio + library) is fabricated (A4), the augmentation library (Albumentations) doesn't exist in this codebase (A8), the border-crop percentage is wrong (A7), best-checkpoint selection criterion is wrong (B4), the Grad-CAM library attribution is wrong (B3), the Groq model name is wrong (D5), and the endpoint names are wrong (D6). The flagship CT accuracy figure (98.19%) traces to a superseded, leakage-contaminated evaluation, not the deployed model (C2).
- **Internal consistency (20%) — mixed.** The document is self-consistent (no contradictions within itself), but its own numbers don't match the codebase's authoritative internal status doc (`PROJECT_STATUS.md`) in several places, and it disagrees sharply with the PPT on completion status (Step 0).
- **Honesty/completeness about limitations (20%) — weak.** Two of the three self-disclosed "weaknesses" in §14 (raw exception leakage, no test suite) are demonstrably false in the current code — meaning the self-disclosure itself needed fact-checking. Meanwhile the project's most legitimate, interesting, and honestly-reportable limitations and fixes (CT patient leakage, scanner-table shortcut, TB artifact severity, the TB accuracy trade-off) are never mentioned at all, despite living in the repo's own `PROJECT_STATUS.md`.
- **Coverage (20%) — good.** Structurally complete against what a Review-1 report should cover (motivation, literature survey, SDG mapping, requirements, design justification, architecture, societal context, limitations, status), with real technical depth in the prose sections that don't depend on the disputed numbers.

### PPT: **6 / 10**

- **Factual accuracy (40%) — moderate-to-good, because it claims less.** Where it commits to specific numbers, they're close to the raw/interim reality (CT ~1,097/110 patients, ✅; CT imbalance ~4.7x, ✅; dedup 56+1 vs actual 58+1, close). It avoids the Report's most severe errors (no false claim about accuracy, no false claim about Albumentations/sklearn/checkpoint-selection criteria) largely by not asserting them yet.
- **Internal consistency (20%) — good.** Every relevant slide (5, 7, 15, 16, 17) consistently frames the project as pre-training/in-progress — there's no internal contradiction, unlike the tension inside the Report's own numbers.
- **Honesty/completeness about limitations (20%) — good in spirit, undermined by staleness.** "To be measured and reported honestly once trained" (Slide 5) and "in progress, not yet confirmed either way" (Slide 15) are honest hedges *for the date the PPT was authored* (metadata: 2026-08-06). But presented today, alongside a codebase that has been fully trained, tested (24 passing tests), and integrated for days, this framing actively misrepresents the current state — an under-claim is still a mismatch with reality, just in the opposite direction from the Report's over-claims.
- **Coverage (20%) — weak.** Because most of the technical work hadn't happened yet at authoring time, the PPT has no results, no confusion matrices, no evaluation evidence, and a "Project Plan & Timeline" slide targeting a "5-Sep" milestone that (per repo evidence) has already been substantially completed. As a submission-ready Review-1 deliverable *today*, this is the PPT's biggest weakness — it needs a full data/results refresh before it can be presented alongside the Report without a reviewer immediately asking which document is true.

**Bottom line:** don't submit either as-is. The PPT needs its entire dataset/results/status content rebuilt to reflect the current, trained, tested, integrated system (the Report's general "we're done" framing is directionally correct and should be the template). The Report needs its dataset tables, split methodology, CT accuracy figure, and §14 self-disclosures corrected against `PROJECT_STATUS.md`, and would meaningfully benefit from actually taking credit for the CT leakage fix and TB artifact remediation — the project's real strengths — instead of the current, partly-wrong self-disclosures.
